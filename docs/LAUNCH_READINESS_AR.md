# AEGIS Security Cloud — إجراءات الاعتماد قبل الإطلاق العام

**الحالة:** نجاح CI شرط ضروري وليس تصريحًا بالنشر. لا تُفتح الخدمة للجمهور قبل اجتياز اختبارات بيئة Staging بإعدادات إنتاج حقيقية وتوثيق نتائجها.

## التوزيع المطلوب
- **واجهة Next.js:** Vercel، جذر المشروع `apps/web`، ومتغير Server-side `API_INTERNAL_URL=https://api-staging.example.com` مع نطاق API حقيقي؛ تأكد من `/api/health` على واجهة Vercel.
- **API:** استضافة سحابية مستمرة تدعم Python 3.12 وFastAPI وHTTPS، مع `WEB_ORIGIN` يطابق الواجهة.
- **البيانات والطوابير:** PostgreSQL مُدار وRedis مُدار؛ اتصالات TLS مع قيود وصول، نسخ احتياطية مشفرة واختبار استعادة.
- **المهام:** scanner وintelligence وscheduler (نسخة واحدة للـscheduler)، وnotifier مستقل بمعلومات SMTP فقط. طابور `notifications` لا يستهلكه scanner.
- **الهوية:** Firebase Auth بمشروع حقيقي وAuthorized Domains وصلاحيات الخادم الأقل، وبريد TLS حقيقي؛ لا ترفع المفاتيح إلى GitHub أو المحادثة.

## شروط GO/NO-GO
1. أحدث `local-core-quality` على GitHub ناجح بالكامل على نفس SHA المرشح للنشر؛ لا يعتمد على تشغيل قديم.
2. تشغيل `scripts/verify_cloud_staging.py` ضد رابط HTTPS حقيقي للواجهة والـAPI المنفصلين؛ نجاح هذا الفحص لا يكفي وحده.
3. إثبات تفعيل Firebase داخل واجهة التطبيق وتسجيل الدخول والخروج واستعادة كلمة المرور، ومراجعة صلاحيات حساب آخر وتقييد الجلسة.
4. فحص نطاق مملوك/مصرّح به فقط: إثبات ملكية ثم تفويض صريح لمسارات محددة ثم تقرير وPDF؛ اختبار سحب التفويض أثناء التنفيذ وإغلاقه.
5. Postgres migrations وRedis workers وCelery beat وnotifier تعمل مع إعادة التشغيل، وتجربة بريد اختياري واستلامه.
6. اختبار دورة AutoFix على مستودع تجريبي مصرّح به، من دون تطبيق تلقائي على الإنتاج؛ preview وstaging وrollback وretest منفصلة بالموافقة.
7. تجربة WordPress SmartVerify على WordPress حقيقي تجريبي وCloudflare DNS TXT مصرح به إن كان مدعوماً؛ لا تستخدم حسابات العملاء للتجربة.
8. نجاح اختبار المتصفح على موبايل وسطح مكتب عبر الخدمات **المنشورة فعليًا**، وليس fixtures وحدها.
9. محاكاة تعطل خدمة/فقد اتصال، التحقق من النسخ الاحتياطي والاستعادة، مراقبة الأعطال والتنبيه، مراجعة البيانات الشخصية ومفاتيح الإنتاج وحماية النطاقات.
10. تعطيل المدفوعات والتسعير والمساعد AI كما هو مطلوب؛ لا تحمل تكلفة خدمة بدون موافقة المستخدم.

**إن فشل بند واحد فالقرار NO-GO** ويظل النشر Staging خاصًا. التحقق CI لا يثبت نجاح تنفيذ Cloudflare أو Firebase أو SMTP الحقيقي أو DNS أو أي خدمة سحابية.
